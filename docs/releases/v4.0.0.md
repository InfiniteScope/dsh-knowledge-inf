# dsh-knowledge v4.0.0 — Directory source identity and safe destructive deletes

This is a reliability release. It closes a real data-integrity defect reported
as issue #20, finishes the local model lifecycle and retrieval-status fixes from
issues #16–#18, and documents profile installation recovery from issue #22.

The major version marks a completed, fully verified reliability upgrade — not a
breaking one. There is no database migration, no forced reindex, no re-embedding,
no legacy directory cleanup, and no model download during upgrade. Existing
0.3.9 data directories start as they are, and every added API is additive.

## One directory source, one sync path

- Re-importing the same local directory no longer builds a second tree. A
  directory source is identified by its knowledge base plus its canonical real
  path, and a later import synchronizes the original root in place.
- One diff engine now serves every path that touches a tracked directory: the
  first import, a repeat import, a single-file reindex, and the base-wide
  background reindex. Previously these four paths each maintained their own
  state, which is how a rescan could report work it had not done and how a
  background reindex could skip tracked roots entirely.
- Files are matched by source path, not by a same-level name guess. A legacy
  child with no stored path is adopted only when its name and kind are unique;
  two candidates are reported as an explicit ambiguity.

## Truthful synchronization results

- Every import and directory reindex returns itemized `created`, `updated`,
  `unchanged`, `deleted`, and `failed` outcomes with relative paths, plus an
  aggregate status of `synced`, `unchanged`, or `partial`.
- Unchanged files are never counted as failures. A sync that updates most files
  while some fail returns `partial` and keeps the successful work, instead of
  wrapping a mostly-successful operation into an overall failure.
- A directory tree that already exists twice for the same source path is
  reported as `ambiguous_source`. It is never merged, moved, or automatically
  deleted: the user inspects and removes the redundant tree.

## Live source identity

- Files imported from a directory retain `sourcePath`, so reindexing one file
  reads it from disk again rather than replaying the stored snapshot.
- Every stored local source path is the resolved real path, for directory trees,
  single files, and repointed sources alike. macOS reaches its temp directory
  through the `/var` symlink and Windows paths may pass through a junction or a
  short name; comparing the spelling a user typed would let one file become two
  sources. The management panel displays the resolved path.
- `sourcePath` is exposed on administrative document summaries and details for
  local sources. Model-facing search results never include it, so server
  absolute paths cannot leak into retrieval evidence.

## Explicit destructive deletes

- `GET /knowledge/documents/:id/delete-impact` reports the directories, files,
  chunks, and durable raw snapshots that a delete would remove, and whether an
  explicit confirmation is required. It is read-only and safe to call before
  showing any destructive interface.
- Deleting a non-empty directory now fails with
  `recursive_confirmation_required` unless the caller passes
  `recursive: true`. The management panel fetches the impact first and shows a
  second confirmation listing the exact scope; the `knowledge_delete_document`
  tool exposes the same `recursive` argument.
- A batch delete preflights every selected root before writing anything, so a
  missing confirmation can never leave a partially deleted batch.

## PDF parsing and the host process

- `pdf-parse` v1 bundles pdf.js v1.10, whose failure path leaks an unhandled
  rejection: `getDocument` throws before the library's local `doc` is ever
  assigned, so its unawaited `doc.destroy()` never runs and the half-built
  worker leaves a promise rejecting with nobody attached. Node 22 escalates that
  stray rejection to a process-level unhandled rejection, so importing a scanned
  or corrupt PDF surfaced an unhandled error in the DSH host — and failed the
  Node 22.19 CI job while every assertion still passed.
- pdf-parse now runs in its own worker thread, the same containment the OCR
  worker already gives Tesseract.js and the embed and rerank processes give
  onnxruntime. The stray rejection is recorded inside that thread and never
  reaches the host, while the caller still receives a clean parse failure and
  falls through to pdfjs-dist layout extraction, OCR, and anydoc as before.
- Each request has a ceiling, so a PDF the engine cannot finish reports a clear
  failure instead of pinning an import indefinitely.

## Local models and retrieval status

- Isolated local embedding and rerank workers recover from a crashed or
  interrupted runtime instead of failing permanently.
- Rerank readiness is finalized after normal inference, and retrieval reports
  the status of each lane so a degraded lane is visible rather than silent.

## Compatibility

- 0.3.9 data directories open without migration, re-embedding, or a forced
  reindex. Existing documents, chunks, embeddings, retrieval contracts, uploads,
  URL imports, and model configuration remain valid.
- Existing fields and call signatures keep working. The sync report, the
  `sourcePath` accessor, the delete-impact endpoint, and the `recursive`
  argument are additions.
- The one deliberate tightening is that a non-empty directory can no longer be
  deleted silently, whether from the panel, the HTTP API, or a model tool.

## Quality

- Complete typecheck and the full Vitest suite pass, including regression
  coverage for canonical source reuse, truthful diff reporting, live-path file
  reindex, ambiguity refusal, and the recursive delete gate.
- The deterministic build, package verification, production dependency audit
  policy, and retrieval benchmark are part of the release preflight.
- Cross-platform CI on Ubuntu, Windows, and macOS, quality CI on Node 22.19, 24,
  and 26, and the real local embedding/rerank smoke run before the tag.

## Documentation

- Both READMEs now document installing a DSH profile and recovering one that was
  installed incompletely (issue #22).
