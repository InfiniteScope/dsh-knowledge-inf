# Issue #17 答复草稿

感谢你做的两组复现。第二组尤其关键——完全没有中断下载、进程里刚刚还正常——它把
"半成品文件"从完整解释降级为其中一个诱因，剩下的解释只有一个：**子进程里的 ONNX
运行时状态坏了，而旧实现会一直复用那个子进程**。你在干净进程里 `require` 同一个
`.node` 能成功，正好印证它是进程内状态。

这个 Issue 的四点诉求都已在 `dsh-knowledge@4.0.0` 中实现。

## 1. 客户端断开不再等于取消下载

下载不再挂在那次 HTTP 请求上：请求立即返回，传输在后台继续，客户端超时或断开既不会
dispose worker，也不会丢掉已经下载的进度。取消是独立接口，并且只对"正在传输"的下载
生效。

## 2. 完整性校验

- 新下载先落在 `.staging/<model>`，只有确认缓存有效之后才用原子 rename 提升到正式
  路径。你在第 3 步看到的那种"正式缓存里躺着 958,794 字节的 onnx"不会再由一次中断的
  下载产生。
- 本地重排模型按**下载器自己上报的字节数**校验权重是否完整（不再是非空 `.onnx` 就算
  已下载）。传输被截断就删掉该缓存；缓存存在但根本加载不了也删掉，下一次重试就是重新
  下载，不再是对着一份坏缓存永久失败。
- 嵌入模型的复用由一份指纹就绪记录把关：指纹覆盖模型目录内每个文件的大小与 mtime，
  且只在子进程真正加载并产出一个探测向量之后才写入。文件被改动过就不会再被当作"已验证"。

## 3. 不需要重启 DSH 就能恢复

这是本次最实质的改动。子进程自己报告的 `load` / `embed` 失败，现在会**替换掉那个子
进程**，而不是留在原地；`embedLocal` 的那次自动重试因此是一次真正的"干净重启"，而不是
在同一个坏进程里再试一遍。这正是 `Module did not self-register` 的解——如你所验证，
新进程里绑定注册是正常的；而旧实现为了省内存刻意保留子进程（空闲只发 `release`），于是
一次失败就让整个进程在剩下的生命周期里永久不可用。

## 4. 失败的任务会出现在 `indexing-status` 里

导入过程中的嵌入失败会把该本地模型状态标记为 `error` 并带上引擎的原始信息，设置里的
轮询能看到，不再"任务消失且没有任何记录"。

## 关于你问的 cancel 语义

现在是明确的：`POST /knowledge/local-models/cancel` **只在确实有下载在传输时才做任何
事**；没有传输时它是 no-op，绝不会删除一个已经完整、已验证的模型（要删模型请用删除
接口）。对一个完整的模型重新下载/重新验证也不会再报成 `downloading`。你提到它曾是
"清除卡死状态的唯一办法"——卡死状态本身已经没有存在的理由（第 3 点）。

## 一个升级时需要你注意的细节

如果你机器上还留着 0.3.9 写进**正式缓存**的那个半成品
`onnx/model_quantized.onnx`（约 958 KB），新逻辑不会自动删除它——我们不替用户删模型
文件。请在"设置 → 本地模型"中删除该模型后重新下载，或手动删除该目录；新的下载会走
staging 再原子替换。

另外有一点我们如实记录为已知限制：**旧版本遗留下来的**缓存无法用"下载器上报的字节数"
校验，因为那个数字只有本次下载才有。对"继承来的可疑缓存"目前做到的是：加载失败就报出
真实原因并替换子进程；重排路径会自动清理该缓存并重下，嵌入路径需要手动删除一次。
