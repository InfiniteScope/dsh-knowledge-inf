# Issue #18 答复草稿

感谢这份报告，尤其是"自检之后只生效一次查询"那三行对照表——它把问题从"模型本身有
问题"定位到了**生命周期**。

三个根因都成立，已在 `dsh-knowledge@4.0.0` 中修复。

## 根因

1. **网关读的是标志，不是模型状态。** `validating` 标志的写入者是重排子进程；子进程
   退出或被替换时没有收尾发布，标志就留在那里，于是 `assertLocalRerankerReady` 一直抛
   `model_checking`——而它拒绝掉的，正是那次本来会写出 `ready` 的检索。这是一个自锁。
2. **例行加载被当成了一次验证。** 子进程每次启动（首次使用、空闲回收之后、切换模型）
   都发布 `validating` / `checking`，并发检索就会被这个"正在验证"挡住。你看到的
   "自检 11ms 就返回、状态却停在 validating"正是这个残留。
3. **`attempted: false` 配 `status: "degraded"` 自相矛盾。** 什么都没尝试却报告"降级"，
   再叠加 `elapsedMs: 0`，调用方无法区分"没跑"和"跑过但失败"，也无法据此采取行动。

## 修复

- **网关以真实状态为准。** `validating` / `downloading` 只在**新鲜**时才被采信（窗口
  2 分钟，按 `statusChangedAt` 计时）；过期的标志直接落到真实检查（权重指纹 +
  持久化的就绪标记）。子进程消失时它会清掉自己发布的状态，界面与检索不再各说一套。
- **例行加载不再发布 `validating`。** 只有真正的自检才宣告"验证中"。
- **新增 `skipped` 状态。** 网关拒绝时报 `skipped`、`attempted: false`，并且**不带**
  `elapsedMs`；只有真正执行过并失败的才算 `degraded`。`status` / `attempted` /
  `elapsedMs` 三者现在自洽。
- **冷启动加载不再被算进查询预算。** 本地重排子进程首次加载约 280MB，而旧实现让这次
  加载与紧随其后的推理共用一个超时；重启后或空闲释放后的第一次查询很容易在加载途中被
  掐断，于是把网关锁成降级——这与你观察到的"自检后只生效一次、随后一直 degraded"最
  吻合。当子进程还没打过分时，超时上额外给 120 秒加载宽限。
- 顺带（与 #16 一起）：`scoreKind` 标注分数的含义，因此"重排概率"和"RRF 融合分"可以被
  区分；重排被跳过时会明确写成 `skipped` 而不是伪装成失败。

## 请你确认

你的触发链条（"每次 reindex 之后状态变 stale"）我们**没有在运行时复现**——那需要真实的
本地重排模型和一个 267 文档 / 8,995 分块的库。上面的修复由单元测试锁定（标志过期、
子进程消失清状态、例行加载不发布 validating、网关拒绝报 skipped、冷启动宽限），但
"reindex → 网关"这条因果链仍需要你在原环境确认。请按原来的流程跑一遍：

1. 重扫目录容器之后立刻 `GET /knowledge/local-models`：状态应很快落到
   `ready` / `healthy`，不会长时间停在 `validating`；
2. **不要先跑自检**，连续做 5–10 次检索：`rerank.status` 应为 `applied`；
3. 如果出现非 `applied`，请把整个 `rerank` 对象贴回来，特别是 `status` / `attempted`
   / `elapsedMs` / `error.code`——现在这四个字段足以区分"网关拒绝""真的失败"和
   "必要的跳过"。
